## Decision

Pari decided (2026-07-12) to implement a GMSK modulator in FPGA HDL (Verilog/VHDL) running in the Zynq PL on the ZedBoard. This is the only path to 10 Mbps — the software/libiio approach has a hard ceiling around 500 kbps.

**Why FPGA:** Gaussian filter + phase accumulator + IQ output run at the AD9361 sample clock in the PL. Zero CPU involvement on the hot path. This is how production radios do it.

## Vivado version-check gotcha (important — causes silent Vivado GUI close)

`hdl_2026_r1`'s `projects/scripts/adi_project_xilinx.tcl` (`adi_project_create` proc, ~line 199) hard-checks the Vivado version against `required_vivado_version` (2025.1). On mismatch it does NOT just warn — it calls Tcl `exit 2`, which kills the entire Vivado process (GUI vanishes with no dialog). This bit us running `adi_project` in the Tcl console on Vivado 2025.2.

**Fix:** before sourcing anything, set `IGNORE_VERSION_CHECK 1` in the Tcl console (GUI flow) — or the `ADI_IGNORE_VERSION_CHECK=1` env var (`make`/batch flow) — which downgrades it to a printed "CRITICAL WARNING" instead of exiting. `project-xilinx.mk` does NOT set this automatically, so the background `make` build kicked off before this fix was found almost certainly died the same way and needs a retry with the env var set.

## Missing IP packaging when skipping `make` (important)

ADI's per-project Makefile (e.g. `projects/fmcomms2/zed/Makefile`) lists `LIB_DEPS` — custom IP cores (axi_ad9361, axi_dmac, axi_clkgen, axi_hdmi_tx, axi_i2s_adi, axi_spdif_tx, axi_sysid, sysid_rom, util_i2c_mixer, util_pack/util_cpack2, util_pack/util_upack2, util_rfifo, util_tdd_sync, util_wfifo, xilinx/util_clkdiv for fmcomms2/zed) that get packaged into Vivado's IP catalog (`component.xml` with a VLNV) via `make` BEFORE the block design (`system_bd.tcl`) ever runs. If you build the project by hand in the Vivado Tcl console (skipping `make`), these IPs are never packaged — block design creation fails with e.g. `ERROR: [BD 41-74] Please specify VLNV when creating IP cell sys_i2c_mixer` the first time it tries to instantiate one.

**Fix used (confirmed working 2026-07-12):** package each `LIB_DEPS` entry directly via Vivado batch mode, one at a time, from inside that library's own directory: `call vivado -mode batch -source <libname>_ip.tcl` (with `ADI_IGNORE_VERSION_CHECK=1` set). This produces `component.xml` in place. All 15 fmcomms2/zed deps (axi_ad9361, axi_clkgen, axi_dmac, axi_hdmi_tx, axi_i2s_adi, axi_spdif_tx, axi_sysid, sysid_rom, util_i2c_mixer, util_pack/util_cpack2, util_pack/util_upack2, util_rfifo, util_tdd_sync, util_wfifo, xilinx/util_clkdiv) packaged successfully this way. Script saved at the session scratchpad as `package_libs.bat` — recreate similarly for other boards/projects by reading their Makefile's `LIB_DEPS` list.

**Transitive LIB_DEPS gotcha:** the top-level project Makefile's `LIB_DEPS` list is NOT the full dependency closure — some libraries have their own `XILINX_LIB_DEPS` in their per-library Makefile that aren't repeated at the project level, because `make` resolves these recursively. For fmcomms2/zed, `axi_dmac` itself needs `util_axis_fifo` and `util_cdc` (see `library/axi_dmac/Makefile`), which caused `create_bd_cell` to fail on `analog.com:user:util_axis_fifo:1.0` subcore even after all 15 top-level LIB_DEPS were packaged. Fix: after packaging the top-level list, `grep -r "XILINX_LIB_DEPS +=" library/` (or just check each dep's own Makefile) to find hidden transitive deps, and package those too before retrying `adi_project`.

**Batch-script gotcha:** `vivado` on Windows resolves to `vivado.bat`. Calling a `.bat` from inside another `.bat` WITHOUT `call` transfers control permanently — the parent script never resumes afterward (it silently exits with the child's exit code once the child finishes). Inside a `for %%D in (...) do (...)` loop this means only the FIRST iteration runs and the loop silently stops, even though the overall script reports exit code 0. Always use `call vivado ...`, not bare `vivado ...`, inside a batch script.

**Also important:** the top-level `make` build (the one kicked off directly, not via the GUI) resolves these same LIB_DEPS through a Makefile rule that shells out to `flock ... sh -c ...`. **`flock.exe` does not exist anywhere on this Windows machine** (not bundled with Vivado, not with Git for Windows) — so plain `make` on this Windows setup will likely hang or fail once it reaches library packaging, even after the Vivado-version-check fix. The Tcl-console / manual-packaging route above is the reliable path on this machine until/unless a `flock`-providing environment (e.g. full WSL) is used instead.

## Milestone sequence (DO NOT SKIP STEPS)

### Step 1 — Get ADI HDL building
```bash
git clone https://github.com/analogdevicesinc/hdl
cd hdl/projects/adrv9361z7035/zed   # check exact path for ZedBoard + AD9361
make                                  # 30–60 min first time
```
Program the resulting `.bit` via Vivado Hardware Manager. Verify `tx_dma_fsk` still works against it. This proves you can build and replace the bitstream.

**Why this first:** You are NOT starting from scratch. The ADI design already has the AD9361 LVDS interface, DMA engines, AXI interconnect. The GMSK block plugs into the existing AXI-Stream TX path.

### Step 2 — Understand the block design
Open the Vivado project. Look at the block diagram (IP Integrator). Understand:
- Where DMA hands off IQ samples to the AD9361 TX path
- The AXI-Stream handshake (TVALID/TREADY/TDATA/TLAST)
- How the DDS core is bypassed when DMA data is present

### Step 3 — Write the GMSK IP block (~200 lines Verilog)
Custom AXI-Stream IP that sits between the PS DMA output and the AD9361 TX path:
- Input: raw bits (1-bit AXI-Stream from DMA)
- Gaussian FIR filter (small, ~5 taps, fixed-point coefficients)
- FM phase accumulator (running sum of Gaussian-filtered phase increments)
- Output: IQ samples (signed 12-bit, AXI-Stream to AD9361 TX FIFO)

### Step 4 — Integrate and test
Wire the GMSK IP into the ADI block design. Rebuild bitstream. Test at increasing data rates.

## First bitstream built (2026-07-12) — but with hold-timing violations

First full build succeeded mechanically (`system_top.bit`, ~3.86MB, in `fmcomms2_zed.runs/impl_1/`), setup timing passed (WNS +0.239ns), but **hold timing failed**: WHS -0.031ns, 11 failing endpoints, "Timing constraints are not met."

**Root cause:** our manual Tcl-console project creation only pasted the `adi_project`/`adi_project_files` lines from `system_project.tcl`, skipping two lines that matter for timing closure on THIS specific project:
```tcl
set ADI_POST_ROUTE_SCRIPT [file normalize $ad_hdl_dir/projects/scripts/auto_timing_fix_xilinx.tcl]
set_property strategy Congestion_SpreadLogic_high [get_runs impl_1]
```
`auto_timing_fix_xilinx.tcl` is ADI's own automated hold-fix (`phys_opt_design -hold_fix` loop + a `route_design` re-run workaround), added specifically because of a **known Vivado 2024.x/2025.x hold-timing regression** (see comments in that script, links to AMD/Xilinx forum threads). This is a known/expected issue for THIS Vivado version, not something we caused.

**Fix (applied via Tcl console, not yet confirmed successful as of last check):**
```tcl
add_files -fileset utils_1 -norecurse [file normalize "$ad_hdl_dir/projects/scripts/auto_timing_fix_xilinx.tcl"]
set_property strategy Congestion_SpreadLogic_high [get_runs impl_1]
set_property STEPS.ROUTE_DESIGN.TCL.POST [get_files auto_timing_fix_xilinx.tcl -of [get_fileset utils_1]] [get_runs impl_1]
reset_run impl_1
launch_runs impl_1 -to_step write_bitstream
wait_on_run impl_1
```
**Result (confirmed 2026-07-12): timing closure achieved.** After wiring in `auto_timing_fix_xilinx.tcl` + `Congestion_SpreadLogic_high` strategy and re-running `impl_1`, the ATF's `route_design`-workaround alone fixed it (0 phys_opt_design attempts needed): WNS +0.249ns, WHS improved from -0.031ns (FAILED, 11 endpoints) to **+0.012ns (PASS, 0 endpoints)**. `write_bitstream completed successfully` ran immediately after against this fixed checkpoint (`ATF_success_system_top_routed.dcp`) — confirmed via `runme.log`. First fully clean bitstream for fmcomms2/zed exists at `fmcomms2_zed.runs/impl_1/system_top.bit`.

**Reporting gotcha:** `system_top_timing_summary_routed.rpt` (the standard post-route report) is NOT overwritten by the ATF post-route script — it stays frozen at the pre-fix (failing) numbers. The real final result lives in `ATF_<n>_final_timing_summary.txt` and `runme.log` ("Auto Timing Fix SUCCESS/FAILURE" line). Always check those, not the plain `_routed.rpt` file, when ADI_POST_ROUTE_SCRIPT is in use.

**Lesson for next manual project recreation:** paste the FULL body of `system_project.tcl` (including the `ADI_POST_ROUTE_SCRIPT`/strategy lines), not just the `adi_project`/`adi_project_files` calls — those two lines matter for timing closure on boards/projects known to have hold-violation issues, and skipping them isn't obvious until you check the timing summary report after implementation.

## Architecture pivot (2026-07-19): board roles swapped, target IP is now RX demodulator not TX modulator

Pari decided to swap TX/RX roles from the original SDR_Link setup:
- **TX now = Pluto+**, staying pure software/C (libiio, precompute-buffer + `iio_buffer_push()`, same technique as `tx_dma_fsk`). No HDL needed on Pluto+.
- **RX now = ZedBoard**, and the custom FPGA IP target shifts from a TX-path GMSK **modulator** to an RX-path GMSK **demodulator** (matched filter + timing recovery (Gardner/Mueller-style) + symbol decision), inserted in the `cf-ad9361-lpc` (RX capture) AXI-Stream path instead of `cf-ad9361-dds-core-lpc` (TX DMA path).

**Why this split:** TX modulation is a batch/precompute problem — the AD9361 DAC clocks out a pre-filled buffer in hardware, decoupled from CPU scheduler jitter, so software TX is tractable even at high rates as long as a frame can be precomputed before its playback deadline. RX demodulation is a genuinely real-time streaming problem — incoming ADC samples must be matched-filtered/timing-recovered/decided continuously with no ability to precompute ahead, which a Cortex-A9 under Linux cannot sustain at high sample rates. This asymmetry (not just "RX has more math") is why RX specifically needs PL and TX doesn't.

**Why ZedBoard gets the HDL work:** JTAG access is currently only available for the ZedBoard, and all the Vivado/ADI HDL environment work already done (fmcomms2/zed project, IP packaging workarounds, timing-closure fix, verified-working bitstream — see below) is built against it. Pluto+ has no JTAG access right now, so it stays as a pure userspace box running its stock bitstream.

**Implication for the milestone plan above:** Steps 2–4 (understand block design → write custom IP → integrate/test) still apply, but Step 3's IP is now a **GMSK demodulator on the RX AXI-Stream path**, not a modulator on TX. The Gaussian-filter-plus-phase-accumulator TX design sketched earlier in this file is deprioritized/moot for the FPGA work — that logic will likely live in the Pluto+ C program instead.

## TX/RX role-swap validated end-to-end (2026-07-19)

After the ZedBoard SD card replacement (see [[project_sdr_devices]]) and re-establishing network access, ran the actual role-swap validation: **TX moved to Pluto+, RX moved to ZedBoard**, reusing the existing `tx_dma_fsk.c`/`rx.c` C apps unmodified (both use `iio_create_local_context()`, no code changes needed — see the architecture-pivot note above for why this split makes sense).

**Method:** compiled both `tx_dma_fsk.c` and `rx.c` natively on the ZedBoard (has gcc; Windows laptop has no ARM cross-compiler), then copied the TX binary over to Pluto+ via `cat`-over-SSH (`rx-deploy-via-zed`-style trick — Pluto+ has no sftp-server so pscp doesn't work, plain cat-over-ssh pipe preserves binary integrity fine). Ran RX in the background on ZedBoard, TX in the background on Pluto+.

**Gotcha hit: `pkill -f <name>` can kill its own SSH session.** `pkill -f rx_arm` matches against the FULL command line of every process, including the invoking shell's own `sh -c "pkill -f rx_arm; ..."` line (which itself contains the string "rx_arm") — it killed itself/the session before the rest of the command could run (symptom: plink exits 128, zero output, even from an unrelated later `echo`). Fix: use `killall rx_arm` (matches process name only) instead of `pkill -f` for this kind of remote one-liner.

**First attempt received only noise** (ΔP flipping small-magnitude and incoherently every ~1ms tick, stuck in `[IDLE|HUNT]` forever) — root cause was **forgetting to physically swap the antennas** to match the new roles. The AD9361/FMCOMMS2 boards have separate TX and RX SMA ports; the antennas were still on the ports matching the OLD roles. Fix: move each board's antenna to the port matching its CURRENT role (Pluto+ → TX port, ZedBoard → RX port).

**After swapping antennas: confirmed working end-to-end.** Clean ΔP swings (~+20dB / ~-20dB, matching real modulation, not noise), full frame sync achieved (preamble → 0xD5 SYNC → LEN → data), decoded payload correctly twice in a row: `>>> HELLO SDR`. ### Gotchas hit packaging + integrating this IP (useful for the next custom IP too)

1. **Tcl `set` is not batch `set`.** `set ADI_IGNORE_VERSION_CHECK=1` inside Vivado's interactive Tcl Shell throws `can't read "ADI_IGNORE_VERSION_CHECK=1": no such variable` — that's cmd.exe/batch syntax, not Tcl. Tcl reaches OS env vars via the `env` array: `set ::env(ADI_IGNORE_VERSION_CHECK) 1`. Also: if Vivado's Tcl Shell is already running interactively, don't re-invoke `vivado -mode batch -source ...` — just `source <script>.tcl` directly in the session you're already in.
2. **`ipx::create_xgui_document` may not exist as a valid command** in this Vivado session/mode (`invalid command name` error) — it only builds the cosmetic "re-customize IP" GUI page and isn't needed for an IP with no configurable parameters. `package_ip.tcl` was fixed to skip it; packaging completes fine via just `ipx::update_checksums` + `ipx::save_core`.
3. **Vivado's Tcl console echoes commands interleaved with their output**, which can look like a crash/failure when it isn't (e.g. `current_project fmcomms2_zed` appearing to "break" a sequence was actually just an echoed return value). **Ground truth is always the filesystem** — check whether `component.xml` (or whatever the expected output file is) actually exists and is well-formed (non-truncated, has the right tags/checksums) rather than trusting a garbled pasted transcript.
4. **`update_ip_catalog` fails while a block design is open**: `Cannot update IP catalog while a BD design is open`. Fix: `close_bd_design [current_bd_design]` -> `update_ip_catalog` -> reopen the `.bd` file.
5. **The hold-timing fix properties persist correctly** across new IP integration work — `get_property strategy [get_runs impl_1]` still returned `Congestion_SpreadLogic_high` and `STEPS.ROUTE_DESIGN.TCL.POST` still pointed at `auto_timing_fix_xilinx.tcl` without needing to redo any of that setup. These are saved per-run in the project, not something a block-design edit touches.

## Step 1 (frequency discriminator) — SIM gate PASSED (2026-07-25)

Implemented `hdl/gmsk_step1_discriminator/gmsk_step1_discriminator.v` per the design doc (`docs/step1_discriminator.html`): delay-and-conjugate-multiply quadrature FM demodulator, AXI4-Stream in/out, one sample per clock, no rate change. Only computes `Im{z[n]*conj(z[n-1])} = Q[n]*I[n-1] - I[n]*Q[n-1]` (2 multiplies, not the full 4-multiply complex product) since the real part is never consumed downstream.

**Interface convention (assumed, not yet confirmed against real hardware):** TDATA packs `{Q[15:0], I[15:0]}`, IQ_WIDTH=16 to match the AD9361 RX chain's native sign-extended word width, OUT_WIDTH=18 (truncates the 33-bit full-precision product down by keeping the top 18 bits). `s_axis_tready` tied high — this is a fixed-rate fabric pipeline with no realistic backpressure scenario, so no stall logic was built. **Must be verified against `axi_ad9361`'s actual output width when this gets wired into the real block design (Step 4 integration)** — this was written and simulated standalone, before that wiring exists.

**SIM gate:** `hdl/gmsk_step1_discriminator/sim/` — `gen_test_vectors.awk` synthesizes a continuous-phase two-tone test stream (MARK=150kHz/SPACE=50kHz per `rf_params.h`, alternating 1,0,1,0,... bit pattern, phase never reset at bit boundaries, matching real continuous-phase FSK) into `test_vectors.hex` ($readmemh format, regenerate via `awk -f gen_test_vectors.awk > test_vectors.hex` — this .hex is gitignored, not committed, since it's trivially regenerable). `tb_gmsk_step1_discriminator.v` feeds it through the DUT and self-checks: each bit segment's output should settle to a clean, consistent level, and MARK's level should be clearly separated from SPACE's (>2x).

**Ran via Vivado's standalone simulator (no project needed):** `xvlog` → `xelab ... -s tb_sim` → `xsim tb_sim -runall`, binaries at `C:\AMDDesignTools\2025.2\Vivado\bin\` (not on PATH — invoke with full path). **Result: TEST PASSED.** MARK segments settled at 4855.0, SPACE at 1658.9 (ratio 2.93x) — matches hand-calculated expected values (`AMPLITUDE^2 * sin(2*pi*f/Fs)`, truncated to OUT_WIDTH) almost exactly, confirming both the Verilog and the small-angle approximation the design doc relies on.

**First bitstream attempt: TIMING FAILED (2026-07-26)** — `WARNING: ATF: Auto Timing Fix FAILURE after 5 attempts - final WNS is -0.870 ns`. This is a genuinely different problem from Step 0's earlier hold-timing regression (which ATF's `route_design` workaround fixed) — this is a **setup** violation, and ATF's fix doesn't target this class of issue. Root cause, read directly from `system_top_timing_summary_routed.rpt`'s worst path:
```
Source:      axi_ad9361/.../adc_data_q0_int_reg[15]/C   (plain register)
Destination: gmsk_step1_discrimin_0/.../mult_qi_reg/A[20]  (DSP48E1 -- Vivado did infer the dedicated multiplier, that wasn't the issue)
Slack: -0.868ns, Logic Levels: 0, Data Path Delay: 1.145ns of a 4.000ns budget
```
**`rx_clk` (the `axi_ad9361_l_clk` net) runs at 250 MHz**, not the 2.304 Msps sample rate as originally assumed — the LVDS interface clock runs far above the actual per-channel sample rate. With "Logic Levels: 0" and a tiny 1.145ns data-path delay, the failure wasn't logic speed — it was **clock network delay** consuming the 4ns budget on a same-cycle hop from `axi_ad9361`'s output register straight into our DSP48, because our RTL multiplied this cycle's *raw* `s_axis_tdata` (a bare wire, zero pipeline stage of our own) against a registered `i_prev`/`q_prev`. One operand had no register stage cushioning the physical distance between the two flip-flops.

**Fix applied:** added a second delay-line stage so BOTH multiply operands come from registers (`i_d1/q_d1` = z[n-1], `i_d2/q_d2` = z[n-2], multiply is now `q_d1*i_d2 - i_d1*q_d2`) instead of one raw wire + one register. Standard technique for feeding a DSP48 at high frequency — gives the placer/DSP48 input pipeline a full cycle at each hop. Costs exactly one extra cycle of latency (3->4), irrelevant to this fixed-rate streaming design. **Re-ran the SIM gate after the change: still TEST PASSED, identical output values (MARK 1213.0 / SPACE 414.0, ratio 2.93x)** — confirms the fix is purely a timing/pipelining change, zero functional difference. Re-packaged the IP (`ip_repo/gmsk_step1_discriminator/component.xml` regenerated).

**Second bitstream attempt: WNS improved to -0.110ns, still FAILED.** The two-register-stage fix worked — the discriminator's own path was no longer in the violated-paths list at all. **Third bitstream attempt: WNS -0.056ns / -0.012ns, still technically FAILED but only inside Xilinx's own encrypted `system_ila_0` netlist** (`<hidden>` path segments — can't be edited). **Tested the hypothesis directly:** copied `rx.c`/`rf_params.h` to the ZedBoard (`192.168.1.104`, current IP as of today — see [[project_sdr_devices]]), compiled natively (`gcc -O2 -liio -lm`), ran it. **Reproduced last session's exact behavior: PHY config step ("Configuring AD9361 RF front-end...", RX LO/buffer creation) completed successfully, then it failed at the same `iio_buffer_refill error: -110`, process exited cleanly (exit code 0).** Re-checked the ILA afterward with a genuine `Full`/`16384 of 16384` capture (not the earlier never-triggered false alarm) — `Res` still read a flat 0. **Conclusion: `rx.c`'s PHY config does NOT release `axi_ad9361_rst`.** It only talks to the SPI-based `ad9361-phy` chip config — a different register space entirely from the FPGA-side `axi_ad9361` core's own control block.

**Root cause found by reading the RTL directly** (`library/axi_ad9361/axi_ad9361_rx.v` → `library/common/up_adc_common.v:239,578`): `assign adc_rst = ~adc_rst_n`, where `adc_rst_n` is a cross-clock-domain copy of a register bit literally named `up_resetn` (`up_adc_common.v:239`, `up_wdata[0]` of an ADI `up_xfer_cntrl`-transferred control register) — a **deliberately software-gated reset** per the RTL's own comment: *"De-assert adc_rst together with an updated control set... important at start-up when a stable set of controls is required."* This bit is normally written once by the **Linux `cf_axi_adc` kernel driver's `probe()`**, not by anything userspace/libiio touches.

**`dmesg` explained why it was never written for our bitstream:** `cf_axi_adc 79020000.cf-ad9361-lpc` probed successfully at `[ 3.217308]` — 3.2 seconds into boot, i.e. against the bitstream loaded from the SD card's `BOOT.BIN` at boot time, NOT our custom `hdl_2026_r1` build (which loads later, live, via JTAG). **Loading a new bitstream via JTAG reinitializes every fabric flip-flop to its power-on value, silently wiping `up_resetn` back to 0 — invisible to Linux, so nothing re-triggers the driver's `probe()`.** This coherently explains everything: why Step 0's `devmem` registers always worked fine (we write fresh values ourselves, no dependency on stale pre-JTAG state), why `cf_axi_adc`'s dmesg line looked like success (it was, just against the wrong/earlier bitstream), and very plausibly the original `-110` DMA mystery itself (a reset-held ADC datapath produces no data for DMA to complete on).

**Fix confirmed live on hardware (2026-08-01):** `echo 79020000.cf-ad9361-lpc > /sys/bus/platform/drivers/cf_axi_adc/unbind` then `.../bind` (same technique tried last session, but that attempt had no way to confirm whether it worked — this time the ILA proved it directly). Unbind and bind both completed in well under a second, no hang (unlike last session's unpredictable 20–90s hangs on similar operations). Fresh `dmesg` line confirmed a real re-probe at `[9758.012153]` (vs. the original `[3.217308]`). **ILA capture (`iladata.csv`, exported by Vivado, landed in `hdl/gmsk_step1a_ila_counter/ip_repo/gmsk_step1a_ila_counter/`, gitignored — not source, safe to leave/delete) caught the exact transition on sample 8192:** `Res` flips 0→1 (TRIGGER marker fires on this exact sample), `count` reads `0000` that cycle then `0001, 0002, 0003...` incrementing by exactly 1 every single subsequent cycle with zero glitches through to `1fff` at the last sample (16383). **This is unambiguous, hardware-confirmed proof of the entire chain:** the counter/clock/reset wiring/ILA/dbg_hub are all completely correct, `axi_ad9361_rst` really is gated by `up_resetn`, and `cf_axi_adc` unbind/rebind really does re-release it.

**Step 1a is essentially answered and then some** — not only is the debug-capture chain proven sound (the original goal), the exercise surfaced and hardware-confirmed the actual root cause of Step 1's original DMA mystery. Re-ran `rx.c` after the `cf_axi_adc` rebind: **`-110` still occurred.** `up_resetn` release alone wasn't sufficient — real progress though, since it hardware-eliminates `axi_ad9361`'s own reset as the (sole) cause and narrows the remaining suspect to the DMA engine itself.

**`axi_dmac` has an exactly analogous software-gated mechanism.** `library/axi_dmac/axi_dmac_reset_manager.v` has a `ctrl_enable` input driving a multi-clock-domain (`dest_clk`/`src_clk`/`sg_clk`) enable/reset sequencer — same pattern as `axi_ad9361`'s `up_resetn`, normally written once by the Linux `dma-axi-dmac` driver's `probe()`. Same theory: JTAG-swapping the bitstream after boot wipes this too, and nothing re-triggers a re-probe.

**Attempted unbind/rebind of the three `dma-axi-dmac` instances (`7c420000.dma`, `7c400000.dma`, `43000000.dma`) — hit a real kernel bug, not just slowness.** First instance unbound instantly (0.003s). Second (`7c400000.dma`) triggered a **NULL-pointer kernel oops**:

```
dma_channel_rebalance from dma_async_device_unregister+0x6c/0x114
dma_async_device_unregister from axi_dmac_remove+0x2c/0x48
axi_dmac_remove from platform_remove+0x40/0x5c
```
This is a genuine bug inside the Linux dmaengine framework's `dma_channel_rebalance()`, hit via `axi_dmac`'s `.remove()` path — a materially different, more serious class of problem than last session's "slow but always recovers" unbind/rebind hangs on `cf_axi_adc`. **Where this leaves the investigation:** the robust fix is almost certainly to stop live-JTAG-swapping the bitstream into an already-booted kernel altogether, and instead bake `system_top.bit` into a persistent `BOOT.BIN` (via a matching FSBL export + `bootgen`) so it's present in the fabric from cold boot, before any driver ever probes — eliminating this entire class of "driver configured against stale/wrong bitstream state" bug for both `axi_ad9361` and `axi_dmac` at once, permanently. **Found and fixed a real bug via direct ILA data analysis, not just eyeballing the waveform.** First capture at RX gain=40dB showed `m_axis_tdata` swinging only 0–4 — traced this to the discriminator's fixed 17-bit output truncation combined with real (non-full-scale) AD9361 sample amplitude (~1000, vs. the sim's near-full-scale synthetic test vectors) — a legitimate gain/precision mismatch, not a bug. Values got visibly bigger, user reported "it is working" — **but pulling the actual capture CSV and cross-tabulating by `tvalid` showed something different: all 4,096 samples where `tvalid=1` were exactly 0, and the nonzero values (27, -2, 26...) the user was seeing only occurred when `tvalid=0`** (invalid/don't-care samples). Ground-truth data contradicted the visual impression.

**Root cause, traced through the RTL:** the delay-line's `i_d2 <= i_d1` shift was gated by a separately-delayed `valid_d0`, firing exactly one cycle after `i_d1` itself had *already* updated to that same new sample — so `i_d2` duplicated `i_d1` instead of holding the genuinely previous sample, whenever idle cycles separated valid pulses (which real AD9361 data always has — sparse ~2.3 Msps strobes within a 250 MHz fabric clock). Two identical I/Q pairs cancel exactly to zero in `Q[n-1]*I[n-2] - I[n-1]*Q[n-2]`, matching the hardware symptom precisely. **The simulation testbench never caught this because it drove `s_axis_tvalid` high on every single clock with zero gaps** — a fundamentally different stimulus pattern than real hardware, which fully masked the bug through every prior SIM-gate pass.

**Fix:** made the `i_d1`→`i_d2` shift atomic (single condition, both updates in the same always-block branch, so `i_d2` captures `i_d1`'s pre-update value per Verilog non-blocking-assignment semantics) instead of splitting it across two cycles via the separate `valid_d0` flop. Latency dropped from 4 cycles to 3 as a side effect. **Also rewrote the testbench** to drive gapped valid pulses (`GAP_CYCLES=3` between samples, not back-to-back) and self-synchronize its capture loop to `m_axis_tvalid` pulses rather than a fixed cycle-latency offset — so this class of bug will get caught in sim next time, not just via real-hardware ILA forensics. Re-ran the SIM gate: identical clean result (MARK 1213.0 / SPACE 414.0, ratio 2.93) now genuinely validated under gapped stimulus. Repackaged the IP.

**Lesson reinforced for this whole project:** always cross-tabulate captured data by its own valid/trigger signal before trusting a visual read of a waveform — this is the second time in one session (after the Idle/`0 of N` false-triggered-capture issue) that "it looks like it's working" turned out to need the raw exported CSV to actually confirm or refute.

**Redeployed and re-tested (2026-08-01) — fix confirmed on real hardware.** Rebuilt (this time timing closed cleanly, `WNS +0.016ns`, SUCCESS after 0 ATF attempts — better than before the fix, suggesting the atomic-shift RTL change also helped placement/routing), redeployed via the `BOOT.BIN` recipe.

**Built two new debug tools to get a clean, unambiguous test signal, both in git:**
- `tx/tx_gmsk_debug.c` — continuous Gaussian-shaped `1,0,1,0,...` transmitter, same MARK/SPACE tones as `tx_dma_fsk.c` (so everything already calibrated against those tones stays valid), precomputes one full period as a phase-continuous buffer and plays it via a libiio **cyclic** buffer (hardware repeats it forever, zero further CPU/DMA involvement) — a genuine "LUT" in the sense the user asked for. Circular convolution (not plain) is required for a glitch-free loop: an equal +1/-1 NRZ count integrates to exactly zero net phase over one period, so the hardware wrap-around is phase-continuous. `GMSK_BT` controls smoothing (**inversely** — higher BT = narrower kernel = less smoothing = more dwell time at the true tones; this is the opposite of what "BT" sounds like it should do, tripped up an initial "lower BT to reduce smoothing" request). ## Fast-bitrate debug mode, a real phase-glitch bug, and a dynamic-range fix (2026-08-02)

## TX-vs-RX FFT comparison caught real ADC clipping, fixed (2026-08-02)

Pari asked whether the TX and RX FFTs "should look almost similar" — answer: the two peaks should land at the same frequencies, but noise floor, cascaded TX+RX filtering, and absolute scale (TX is unitless computed samples, RX is real ADC counts after gain) all mean they won't look identical even when everything's working. Built the actual comparison to check anyway:
- `tx_fft_dump.c` (scratchpad, not committed): standalone, regenerates the exact same NRZ -> Gaussian filter -> phase-integration math as `tx_gmsk_debug.c` and dumps N samples to CSV, no hardware touched.
- `rx_iq_dump.c` (scratchpad, not committed): same RX config as `rx_spectrum_check.c`, dumps raw ADC I/Q counts instead of computing Goertzel power.
- Interactive Chart.js widget: windows both with a Hann window, computes a direct DFT (not FFT -- O(N^2) is trivial in-browser at N=1024, and it sidesteps needing power-of-2-friendly sample counts), overlays TX/RX magnitude in dB normalized to each one's own peak.

**Found real ADC clipping from the raw data alone, before even building the FFT.** RX I/Q samples were pinned at exactly +-2047/2048 (the 12-bit ADC's hard ceiling) an enormous fraction of the time -- a direct consequence of the TX power bump (-20dB -> -3dB, ~17dB) without correspondingly pulling RX gain back down. ## Discriminator OUT_WIDTH widened 16->24 to fix the truncation/dynamic-range issue (2026-08-02)

Root cause of the range-14 discriminator output (previous entry): `m_axis_tdata <= imag_full >>> TRUNC_SHIFT` at [gmsk_step1_discriminator.v:159], where `TRUNC_SHIFT = PROD_WIDTH - OUT_WIDTH = 33 - OUT_WIDTH`. With `OUT_WIDTH=16`, `TRUNC_SHIFT=17` — sized for near-full-scale (+-32767) synthetic sim inputs, but real AD9361 samples only reach ~+-2039 (~11 significant bits), so the 33-bit product only ever populates ~23 bits; shifting away the top 17 discarded exactly the bits real data actually used.

**Decided against both a hand-tuned static shift and true adaptive/dynamic AGC** (the latter would need a leading-zero-counter-based scale that travels downstream as sideband metadata — real complexity, and pointless here since `rx.c`/`rx_spectrum_check.c` both set `gain_control_mode=manual` and write `hardwaregain` once at startup, never changing mid-run — confirmed by reading both files). **Instead: just widen `OUT_WIDTH` from 16 to 24** (still byte-aligned, legal for AXI4-Stream TDATA — 16 was originally picked because it matched IQ_WIDTH, not because 16 was special). `TRUNC_SHIFT` drops to `33-24=9`, comfortably covering the ~23 bits the product actually populates at real (non-full-scale) amplitudes, without needing to know or tune to the exact current gain setting. Near-zero cost since nothing downstream consumes the discriminator's output yet (Step 2/3 don't exist) — the ILA probe is the only current consumer and gets reconfigured to 24 bits next time it's wired back up (routine IP-customization step, not a Verilog change).

**Changed:** `gmsk_step1_discriminator.v` (`OUT_WIDTH` default 16->24), `sim/tb_gmsk_step1_discriminator.v` (`OUT_WIDTH` localparam 16->24, must always match the DUT). **SIM gate re-run and PASSED**: MARK avg 310741.5 / SPACE avg 106196.2, ratio 2.93 — same ratio as always, absolute values ~256x bigger (2^8, matching the 8-fewer-bits shift) confirming the change is purely a scale/precision change, zero functional difference. **Repackaged the IP** (`ip_repo/gmsk_step1_discriminator/component.xml` confirmed `OUT_WIDTH` default now 24 at both the model-param and user-param level).

**Not yet done:** re-wiring the discriminator (with its new 24-bit `m_axis_tdata`) back into the `fmcomms2_zed` block design (it's currently still wired at the old 16-bit width from the 2026-08-02 ADC-clipping session) — needs the `system_ila_0` probe0 width bumped from 16 to 24 bits, rebuild, redeploy via `BOOT.BIN`, re-check the ILA capture's dynamic range against the same de-clipped RX gain (25dB) used in the last hardware test. **This is exactly where to resume next session.**

## Major requirements pivot (2026-08-02): 10 Mbps GMSK / 4 samples-per-symbol target, FHSS + FEC on the roadmap

Pari set the real end-goal requirements, a big jump from the current bring-up link: **10 Mbps, true GMSK (Gaussian-filtered, not the bring-up link's 2-FSK), 4 samples/symbol** — implying a **40 Msps** ADC/DAC rate (vs. today's 2.304 Msps) and a **~1150x drop in samples/symbol** (4608 -> 4). Plus, as later phases: **frequency-hopping spread spectrum (FHSS)** and **forward error correction (FEC)**.

**Why this matters architecturally, not just numerically:** at today's 4608 samples/symbol, timing recovery is barely necessary — almost any fixed sample offset works, which is exactly why the discriminator output looks so clean on the ILA right now. At 4 samples/symbol, that headroom is gone; picking the wrong instant is the difference between a clean eye and garbage. So the interpolator+Gardner timing-recovery loop (being designed now, see the roadmap doc) goes from "nice to have" to "load-bearing." It also invalidates any decimation-factor math sized for the old oversampling ratio (e.g. a decimate-by-576 idea floated before this pivot) — at 4 sps there's no oversampling left to decimate away; the loop must run at (or barely above) the symbol rate itself. TX-side work is also newly in scope: `tx_dma_fsk.c`/`tx_gmsk_debug.c` are 2-FSK, not Gaussian-filtered GMSK — true GMSK needs a TX-side Gaussian pulse-shaping filter that doesn't exist yet.

**Roadmap doc updated** ([docs/rx_roadmap.html](../../docs/rx_roadmap.html)): added a "Target link requirements" panel up top (10 Mbps / GMSK / 4 sps / 40 Msps, FHSS+FEC called out), relabeled the existing frame-cadence panel as "current bring-up link" (kept factually as-is — Steps 0-1 really are validated against the 500bps/4608-sps link, that history shouldn't be erased), and appended three new planned steps: **Step 7** (rate/modulation upgrade to real 10 Mbps GMSK), **Step 8** (FHSS), **Step 9** (FEC). ## Sub-step A (Farrow interpolator core) built, real Verilog width-inference bug found and fixed (2026-08-02)

Built `hdl/gmsk_step2a_interpolator/gmsk_step2a_interpolator.v` per the [[project_fpga_gmsk_plan]] sub-step breakdown for Step 3 (interpolator+Gardner): standalone, open-loop cubic Farrow (Lagrange) interpolator, `mu` supplied via a plain streaming input port (`mu_in`) rather than a real NCO — this IS the real interpolator core (not throwaway test code), the closed loop later just feeds it a time-varying mu instead of a fixed test value. AXI4-Stream in/out, same convention as `gmsk_step1_discriminator`.

**Math derivation (cubic Lagrange through 4 points x[-1..2]):** `v0=x[n]`, `v1=(-2x[-1]-3x[0]+6x[1]-x[2])/6`, `v2=(x[-1]-2x[0]+x[1])/2`, `v3=(-x[-1]+3x[0]-3x[1]+x[2])/6`, evaluated via Horner `y=((v3*mu+v2)*mu+v1)*mu+v0`. Verified independently in Python against an exact cubic polynomial (interpolation of a true cubic must reproduce it exactly at any point) before writing any RTL — confirmed exact match, so the algebra itself was never in question.

**Real hardware bug found via SIM (not the algebra):** first SIM run passed trivially at mu=0.0 (Horner's mu=0 case reduces to `y=v0` regardless of whether the multiply-accumulate stages work at all — a blind spot in testing only mu=0 first) but failed hard (~10% of amplitude, not a rounding-scale error) at mu=0.25/0.5/0.75. Traced via `$display` hierarchical probes at each pipeline stage, cross-checked against a Python model that mirrors the RTL's own delay-line indexing exactly: stage 3 (`v3*mu+v2`) was correct, stage 4 (`acc_3*mu+v1`) was not.

**Root cause — a genuine Verilog width-inference pitfall, confirmed by direct A/B test:** the exact same arithmetic (`acc3=-40447, v1=60492, mu=16384/65536=0.25`) written as a chained inline expression `((acc3*mu)>>>MU_WIDTH)+v1` gave a wrong answer (66764 instead of the correct 50380 — off by exactly `mu` itself, 16384, suggesting a spurious extra term), but broken into explicit, fully-width-declared intermediate wires (`raw_prod`, `shifted`, computed separately) gave the correct answer with the identical values. XSIM does not reliably give a `(multiply >>> shift) + add` chain its full natural width when nested inline feeding a narrower target register, despite `>>>` nominally being a self-determined operator per the Verilog LRM. **Fix:** every multiply-then-shift in the Horner chain (stages 3, 4, 5) now goes through an explicit `PROD_WIDTH`-sized intermediate wire (`prod_N`/`shifted_N`) before being added to the next coefficient — never a single chained expression. **General lesson for this project: any future multiply-accumulate chain should use this same explicit-intermediate-signal pattern, not compact inline expressions, even when the algebra and bit-width budgeting are independently verified correct on paper.** This is a different, more subtle class of bug than the discriminator's real-hardware delay-line timing bug — that one was a logic/timing error the simulator would have caught with the right stimulus; this one is a case where the RTL text *looks* correct and even simulates *partially* correctly (mu=0 case) while being silently wrong for the general case, only caught by actually cross-checking numeric output against an independent reference.

**SIM gate PASSED after the fix:** max deviation 607 out of amplitude 300000 (~0.2%) across all four mu phases (0.0/0.25/0.5/0.75), matching the expected small cubic-approximates-sine residual almost exactly (verified independently in Python before trusting the RTL number). Test vectors (`sim/gen_test_vectors.py`) use a sine wave, not the discriminator's MARK/SPACE bimodal signal — a sine has an exact analytic value at *any* fractional sample position, letting this test check genuine sub-sample interpolation accuracy against ground truth, which a bimodal "settles near a level" test can't do. Testbench uses gapped (non-back-to-back) valid pulses from the start, learning proactively from the discriminator's real hardware bug rather than needing hardware to teach the same lesson twice.

**IP packaged** (`ip_repo/gmsk_step2a_interpolator/component.xml`, confirmed `mu_in`/`MU_WIDTH` present as a standalone port alongside the auto-inferred `s_axis`/`m_axis` bus interfaces). Not yet wired into any block design — sub-step A is pure SIM-gate territory per the breakdown; hardware integration isn't planned until the full closed loop (sub-step F) exists.

**Sub-step A is done.** Per the breakdown in [[project_fpga_gmsk_plan]]'s "next stage" discussion: next is sub-step B (NCO/phase accumulator, standalone) or sub-step D (Gardner TED, standalone) — either can go first, both are independent of each other and of this interpolator core.

**Real, non-cosmetic timing failure found on the FIRST rebuild after wiring it in — WNS -20.296ns**, a completely different class from the earlier "encrypted ILA netlist only" low-risk failures accepted elsewhere in this project. **Root cause: the earlier width-inference fix (see prior entry) over-corrected.** Every Horner stage's product wire had been given the same generously-oversized `PROD_WIDTH = ACC_WIDTH + MU_WIDTH + 1` (47 bits), including Stage 3, whose real multiplicand (`v3_2`) is only `NUM_WIDTH` (28 bits) wide, not `ACC_WIDTH` (30). That extra padding broke Vivado's DSP48 pattern-matching for the smaller multiply.

**Fix:** split each Horner stage into two pipeline stages instead of one -- an "a" stage that registers the raw multiply's output directly into a *naturally*-sized register (operand widths summed, zero padding: `PROD3_WIDTH=NUM_WIDTH+MU_WIDTH+1=45` for stage 3, `PROD_WIDTH=ACC_WIDTH+MU_WIDTH+1=47` for stages 4/5), and a "b" stage that does the shift+add into the Horner accumulator. Registered-in/registered-out around the multiply, nothing else sharing that cycle, is what reliably gets Vivado to infer a real DSP48 -- the same lesson `gmsk_step1_discriminator`'s own real-hardware timing bug already taught (both MAC operands registered), one level deeper this time (the *output* needs its own dedicated register too, not just the inputs). Costs 3 extra pipeline cycles (one per Horner stage, 8 total now vs. 5) -- irrelevant to this fixed-rate streaming block. **SIM gate re-run: identical result to before the fix** (max deviation 607.0, TEST PASSED) -- confirms this was purely a timing/pipelining change, zero functional difference, exactly as intended. IP repackaged.

**Where this actually left off (updated 2026-08-02, later same session):** the DSP48-inference fix above was real but insufficient on its own -- it took two more rebuild cycles and a second, different root cause to actually get a clean bitstream. Full account below.

## Scripted Vivado batch rebuilds, a `create_ip_run` batch-mode quirk, and a second real synthesis bug (SRL extraction) (2026-08-02)

Rather than keep relaying Tcl through the user's interactive GUI session, started driving full bitstream rebuilds directly via `vivado -mode batch -source <script>.tcl` from Bash (`run_in_background`) -- genuinely faster iteration once the wiring itself was believed stable, no back-and-forth pasting required.

**`create_ip_run` fails in batch mode with `ERROR: [Vivado 12-3451] The given file isn't marked synthesis generation` -- reproduced 3 times, across variations (with/without `reset_target`, with/without explicit `open_bd_design` first).** The identical Tcl sequence (`reset_target` -> `generate_target -force` -> `export_ip_user_files` -> `create_ip_run`) that worked fine when the user ran it manually in an interactive GUI Tcl console (fixing the ILA probe width, earlier this file) reliably fails when run from a batch-mode script with no prior GUI session. Root cause not fully understood (something about `.bd` fileset "used in synthesis" state that an interactive session has implicitly and a fresh batch `open_project` doesn't) -- not resolved, **worked around instead**: drop `reset_target` and `create_ip_run` entirely, rely on `generate_target all -force` alone to mark IPs stale, and let `launch_runs impl_1 -to_step write_bitstream` auto-detect and launch whatever IP-level OOC synthesis it needs as a prerequisite. This is also just the more standard/common pattern for scripted Vivado builds. **Working script pattern, worth reusing as-is next time a batch rebuild is needed:**
```tcl
set ::env(ADI_IGNORE_VERSION_CHECK) 1
open_project $proj_path
update_ip_catalog -rebuild
set bd_files [get_files -of_objects [get_fileset sources_1] */system.bd]
generate_target all $bd_files -force
export_ip_user_files -of_objects $bd_files -no_script -sync -force -quiet
reset_run synth_1
launch_runs impl_1 -to_step write_bitstream -jobs 4
wait_on_run impl_1
```

**First rebuild with this working script: still WNS -20.035ns, but the failing path had genuinely moved** (confirmed the DSP48 multiply-width fix from the entry above DID take effect this time -- the new violation involved `v1_3a_reg`, a signal that only exists in the redesigned two-sub-stage-per-Horner-stage RTL). New root cause, a completely different Vivado behavior: `x_1_reg[4]` -> `v1_3a_reg[25]_srl2___inst_valid_d2_reg_r_srlopt`, 38 logic levels, 27 `CARRY4`s. The `_srlopt` name is the tell -- Vivado's synthesizer recognized the "just carry v1 forward unchanged for 2-3 cycles" pattern (`v1_3a<=v1_2`, `v1_3b<=v1_3a`, `v1_4a<=v1_3b`, an inherent side effect of splitting each Horner stage into a multiply-then-shift+add pair) as a textbook shift-register, and opportunistically converted those flip-flops into a compact SRL16/32 primitive -- a space-saving optimization that then placed/routed badly against the neighboring CARRY4-heavy multiply logic.

**Fix: `(* srl_style = "register" *)` on every pure "carry this value forward N cycles unchanged" register** across the whole module (all the `v0_*/v1_*/v2_*/mu_*/valid_*` forwarding chains in stages 3a/3b/4a/4b/5a, plus `mu_d1/valid_d1/mu_d2/valid_d2` in stages 1/2 defensively, even though those are lower-risk being consumed only 1 cycle later). Deliberately did NOT mark `x_m1/x_0/x_1/x_2` (the actual sample delay line) -- those taps are read directly by Stage 2's combinational math every cycle, so Vivado can't SRL-extract them regardless (SRL extraction only applies when intermediate taps are otherwise unused), confirmed by the violated path's *source* being a plain `x_1_reg`, not an SRL. **SIM gate re-run: identical result again** (max deviation 607.0, TEST PASSED) -- synthesis attributes have zero effect on simulation, exactly as expected. IP repackaged.

**Lesson for this whole project, not just this block:** a pipeline stage that looks like "just delay this signal a few cycles, no computation" is exactly the pattern Vivado's synthesizer will try to compact into an SRL by default -- worth adding `srl_style="register"` proactively on any future multi-cycle forwarding chain (Gardner's loop filter/NCO will very likely have several) rather than waiting to rediscover this the same way.

**Update: the SRL fix alone was not sufficient either.** Rebuilding with it applied did produce a genuinely different WNS (-19.709ns, not the frozen -20.035ns repeat from before) -- confirming a real fresh synthesis -- but still badly violated. See the next entry for the third bug found and the eventual interrupted-build handoff.

## Sub-step B (NCO/phase accumulator) built, SIM gate PASSED (2026-08-15)

Pari chose sub-step B (NCO) over sub-step D (Gardner TED) as the next piece to build, when asked which to tackle first (memory had left it as an explicit open fork). Built `hdl/gmsk_step2b_nco/gmsk_step2b_nco.v`: a free-running modulo-1 phase-accumulator NCO -- the standard "strobe-on-overflow" symbol-timing scheme (Rice's *Digital Communications*; also the modulo-1 counter in Mengali & D'Andrea). A single `STEP_WIDTH`-bit accumulator, scaled so 2^STEP_WIDTH = one symbol period, advances by `step_in` (nominally 1/sps) each `sample_valid` pulse; whenever it would cross its wrap point, `strobe` pulses for that one sample and the wrapped remainder becomes `mu_out` -- feeds `gmsk_step2a_interpolator`'s `mu_in` directly, same [0,1) convention, same width (MU_WIDTH=16).

**Deliberately no s_axis/m_axis AXI4-Stream naming**, unlike every other IP in this project so far -- this core carries no data payload (no tdata), only a "sample arrived" pulse, so there's nothing for Vivado's packager to hang a real bus interface off. Plain ports (`sample_valid`, `strobe`) instead, same category as the interpolator's own `mu_in`.

**Unit-conversion insight (why mu extraction is a bare bit-select, zero hardware cost, not a multiply/divide):** `step_in` is 1/sps expressed as a fraction of a SYMBOL period; the wrapped remainder is therefore also in symbol-period units, but `mu` needs SAMPLE-period units. Since one symbol = exactly `sps` samples, converting is multiplying by sps -- free in fixed point when sps is a power of 2 (`LOG2_SPS` parameter, default 2 = 4 sps, this project's actual target), just a shifted bit-select (`new_phase_w[HIBIT:LOBIT]`). Documented as a deliberate, standard approximation once `adj_in` (the future loop-filter correction) is nonzero: rescaling by the *nominal* sps instead of the true instantaneous one, same class of accepted approximation as `gmsk_step2a_interpolator`'s RECIP6 constant.

**`adj_in` threaded through now** (signed correction added to `step_in` before accumulating, tied to 0 in this sub-step's own SIM gate), so the real Gardner loop filter plugs in directly at sub-step F with no redesign -- same "build the real core now, exercise standalone first" philosophy the interpolator used for its own `mu_in` port. Documented (not hardware-enforced) precondition: `|adj_in| << step_in`, so the accumulator never underflows below 0 or wraps more than once per sample.

**No DSP48/SRL/hi-lo-split lessons apply here** -- this design has zero multiplies (just one wide add), so none of `gmsk_step2a_interpolator`'s six real-hardware timing bugs are relevant; a single registered pipeline stage is comfortably fast at 250MHz even at STEP_WIDTH=32.

**SIM gate: two real testbench-timing bugs found and fixed, both genuine Verilog scheduling races, not RTL bugs** (the RTL itself, cross-checked against a bit-exact Python mirror of its own fixed-point formula in `sim/gen_test_vectors.py`, was correct from the start) -- worth remembering for any future testbench in this project:
1. **A same-edge multiple-process race**: an early version used a separate driver process plus a `forever @(posedge clk)` checker process gated by a hand-rolled "delayed valid" signal. Reading a DUT output right after a process's own `@(posedge clk)` resumes is only well-defined once BOTH the Active region (blocking assignments) AND the NBA region (this module's own `<=` commits) have settled for that time step -- confirmed directly with a `$strobe`-based debug probe (which the LRM specifically guarantees samples only after that settling, unlike plain `$display`, which in this simulator appeared to -- misleadingly -- show settled values too on a first pass, then didn't once a second process was added). **Fix: single unified drive+check process** (not two racing processes) **plus an explicit `#1` delay after every `@(posedge clk)` before reading any DUT signal for comparison** -- the standard, unambiguous idiom.
2. **A second, separate race in the drive loop itself**: `repeat(GAP_CYCLES) @(posedge clk);` returns control EXACTLY at a clock edge; the very next statement (blocking-assigning `sample_valid` for the following sample) then executed in that SAME time step, racing the DUT's own always block ALSO triggered by that identical edge -- manifested as `sample_valid` appearing held high for two consecutive edges instead of one (caught via the same `$strobe` trace). **Fix: always land a nonzero `#1` delay after ANY `@(posedge clk)` before touching an input again, never exactly on the edge.**

**General lesson for this project's future testbenches (Gardner TED, loop filter, closed loop):** never assign an input signal via blocking assignment immediately after a bare `@(posedge clk)` returns, whether driving a new stimulus or checking a DUT output — always insert a small settle delay (`#1`) first. This is a more general/robust rule than the self-synchronizing-on-tvalid pattern earlier IPs used, and would have prevented both bugs from ever being written.

## Sub-step D (Gardner TED) built, SIM gate PASSED including a physical-meaning check (2026-08-15/16, after a laptop crash -- nothing lost, both repos were already committed+pushed before it happened)

Built `hdl/gmsk_step2d_gardner_ted/gmsk_step2d_gardner_ted.v`: the Gardner timing-error detector, `e[n] = (y_on[n]-y_on[n-1]) * y_mid[n]` (Gardner 1986 / Mengali & D'Andrea). Takes externally-supplied interpolated samples tagged `is_midpoint` (expected strict alternation ON,MID,ON,MID,... -- documented precondition, not hardware-enforced, matching this project's usual style), outputs the error once per ON-TIME sample (symbol rate). Does NOT compute y_on/y_mid itself (that's `gmsk_step2a_interpolator`, evaluated at two different mu values) and does NOT drive the NCO's `adj_in` (that's the not-yet-built loop filter, sub-step E) -- purely the arithmetic core, same "standalone, externally-supplied stimulus" philosophy every sub-step so far has used.

**DSP48/timing lessons applied proactively this time, not rediscovered.** `diff` (IN_WIDTH+1=25 bits) fits DSP48E1's 25-bit "A" operand whole; `y_mid` (IN_WIDTH=24 bits) exceeds the 18-bit "B" limit and gets the same hi/lo split (LOBITS=15, same split point) `gmsk_step2a_interpolator`'s own multiplies eventually needed after six real-hardware bugs. Applied from the very first version of the RTL here -- zero DSP48-inference bugs expected at synthesis time as a result (not yet built/timed on real hardware to confirm, but the pattern has held for six previous SRL/DSP48 fixes elsewhere in this project, so there's real reason to expect it holds here too).

**Test signal, chosen to be representative not just convenient:** a sum of alternating-sign Gaussian pulses, one per NRZ symbol (`y(t) = sum_k (+1)^k * exp(-(t-kT)^2/(2*sigma^2))`) -- a faithful stand-in for what this project's real discriminator output looks like for a real "1,0,1,0,..." pattern (each symbol contributes one Gaussian-shaped instantaneous-frequency bump, alternating sign), not an arbitrary convenience function the way the interpolator's own sine-wave test was (chosen there specifically because a sine has an exact value anywhere -- here the choice is about physical representativeness instead, since Gardner's algorithm is specifically about detecting mistimed symbol transitions).

**Two independent things verified, same two-tier rigor the interpolator's y(0)=x[n]/y(1)=x[n+1] boundary-condition check established:** (1) bit-exact match against a Python mirror of the RTL's own fixed-point arithmetic, across 3 scenarios (eps=0 "locked", eps=+0.15T, eps=-0.15T -- a constant timing offset applied to every sample position, simulating an untracked loop error) x 60 symbols each, 183 real output pulses total, zero mismatches. (2) A genuine physical-meaning check, not just internal self-consistency: average Gardner error per scenario came out **exactly 0.0 at eps=0 (locked), and +461513.0 / -461514.0 at +eps/-eps** -- symmetric, sign-flipped, matching timing-recovery theory's prediction that Gardner's error is near-zero when locked and signed according to early/late sampling direction. Both the Python reference model AND the actual RTL simulation independently produced these same three numbers.

**Two real testbench-timing bugs found and fixed, both preventable by lessons already on record -- worth reinforcing:**
1. An early version reused `gmsk_step2b_nco`'s single-process "check one cycle after driving" testbench pattern directly. That pattern only worked there because that DUT is a single register stage -- **this DUT is a 5-stage pipeline** (tag-dispatch -> split -> multiply -> recombine -> truncate), so a fixed 1-cycle latency assumption was wrong from the start (manifested as every single check failing, alternating got/expected). **Fix: switched to the PROVEN self-synchronizing capture pattern** `gmsk_step1_discriminator`'s and `gmsk_step2a_interpolator`'s testbenches already use -- a separate `forever @(posedge clk)` process capturing `m_axis_tdata` into an array whenever `m_axis_tvalid` pulses, completely independent of drive timing, compared against a pre-filtered `expected_ontime.hex` (one entry per real output pulse) rather than trying to correlate against a per-input-sample `expected_valid` bitmap. This is NOT the same class of bug as the NCO's own two testbench races (which were about a hand-rolled delayed-marker signal racing the DUT's NBA update) -- reading a DUT's own already-synchronous (tvalid,tdata) pair directly sidesteps that whole class of problem, which is exactly why this pattern was safe here without needing the `#1`-after-every-edge discipline for the CAPTURE side (still used it on the DRIVE side, out of habit/safety, no downside to it there).
2. A Tcl quoting bug in `package_ip.tcl`'s own description string: writing `e[n]` inside a double-quoted Tcl string triggers command substitution on `[n]` (Tcl doesn't know "square brackets in math notation," only "square brackets mean run this as a command"), crashing the script with `invalid command name "n"`. **Fix: use `{...}` (brace-quoted, no substitution at all) for any `set_property` value that might contain non-Tcl-safe characters, and avoid square-bracket math notation in descriptions generally** (used `e(n)` instead) -- worth remembering for any future IP description string in this project.

**IP packaged** (`ip_repo/gmsk_step2d_gardner_ted/component.xml`, 18KB, well-formed, both `s_axis`/`m_axis` AXI4-Stream bus interfaces auto-inferred correctly with the `ASSOCIATED_BUSIF` fix applied same as every other stream IP in this project). Not yet wired into hardware -- same status every sub-step has had at this point, hardware integration isn't planned until each piece is proven standalone first (though sub-steps A and B both later got real standalone hardware bring-up ahead of the full closed loop, so this may follow the same path rather than waiting strictly for sub-step F).

## Architecture decision: mid-point-sample generation, for sub-step F (2026-08-16)

Before sub-step E/F, nailed down a real open question: `gmsk_step2a_interpolator` currently only ever produces ONE output stream (whatever `mu_in` is set to), but `gmsk_step2d_gardner_ted` needs TWO interleaved streams -- on-time samples and mid-point samples (exactly half a symbol apart) -- tagged via `is_midpoint`. Two options were weighed:

- **Option A (chosen): extend `gmsk_step2b_nco` to detect a SECOND threshold crossing** (0.5, not just 1.0/wrap) from the SAME phase accumulator, emitting a companion `is_midpoint` tag alongside the existing `strobe`/`mu_out`. Reuses the single already-validated interpolator instance unchanged -- since it recomputes an output every real ADC sample regardless, feeding it the right `mu` at the right cycle (twice per symbol instead of once) is all that's needed.
- **Option B (not chosen): a second `gmsk_step2a_interpolator` instance**, fed the same discriminator stream but time-shifted half a symbol behind, with its own independent `mu_in`. Keeps the NCO untouched, but roughly doubles the interpolator's DSP48 footprint (already this chain's heaviest core, six real-hardware timing bugs' worth of Horner MACs) and needs careful bookkeeping to get the two instances' relative delay-line phasing correct.

**Why Option A, concretely -- correction (2026-08-16, verified numerically before implementing):** the session that made this decision described the mechanism as "double the accumulator, reuse the bit-select on the doubled value" -- **that specific mechanism was wrong**, caught by writing a Python check against an independent floating-point ground truth (999 crossing events, both exact and perturbed `adj_in` cases) before trusting it enough to write RTL. The actual, even simpler mechanism: **the exact same `[HIBIT:LOBIT]` bit-select on `new_phase_w`, completely unmodified, already gives the correct `mu` for BOTH the on-time (1.0/wrap) and mid-point (0.5-cross) events -- no doubling, no extra shift, no new arithmetic at all.** Why this works: the mid-point mu formula is `(x-0.5)*sps*2^MU_WIDTH` where `x` is the post-crossing phase fraction; expanding that out, it equals the on-time formula (`x*sps*2^MU_WIDTH`) minus `0.5*sps*2^MU_WIDTH` -- and since `sps` is always even (a power of two, `LOG2_SPS>=1`), that subtracted term is an exact integer multiple of `2^MU_WIDTH`, so it vanishes completely under the MU_WIDTH-bit truncation the hardware already does. The only NEW logic needed is the threshold-crossing detection itself (comparing the accumulator's top bit before/after the add to catch a 0.5 crossing, alongside the existing carry-out for the 1.0 crossing) -- genuinely cheaper than sub-step B's own original design implied. Given `step_in` stays comfortably under 0.5 (sps>=2 always), the two crossings are mutually exclusive within any single cycle -- never both fire the same cycle, so a single `strobe`+`is_midpoint`+`mu_out` output triple represents either event cleanly, matching the interleaved ON,MID,ON,MID... protocol `gmsk_step2d_gardner_ted` already expects.

**Lesson worth keeping:** the original "double the accumulator" explanation sounded plausible and self-consistent when reasoned through in prose, but was never checked against an independent numeric ground truth before being written into memory and relayed to Pari as the design rationale -- a real instance of the exact failure mode this project's own SIM-gate discipline exists to catch, just applied one level up (an architecture *decision*, not yet any RTL) before any code existed to test. Caught it before implementing, not after -- worth verifying any similar "I worked out the math in my head" architecture claim numerically before committing to it, even when nothing has been built yet.

**Cost of this choice, worth remembering:** this means `gmsk_step2b_nco` -- already hardware-validated (see the entries above) -- gets a real revision (likely "sub-step B2" or a new port-compatible version) rather than staying frozen, unlike Option B which would have left it untouched in favor of a clean new module. Re-validation (SIM gate + hardware) of the revised NCO will be needed before trusting it again, same as any other RTL change in this project.

**Not yet implemented** -- this is the architecture decision only, not the RTL. Next: design and build the revised NCO (dual on-time/mid-point threshold detection), likely before or alongside sub-step E (loop filter).

## New module: gmsk_interp_tag_delay -- interpolator latency-matching glue, needed before B2 could wire into the TED for real (2026-08-16)

Wiring `gmsk_step2b2_nco` straight into `gmsk_step2d_gardner_ted` (replacing the degenerate `is_midpoint=0` baseline) surfaced a real integration problem, caught BEFORE wiring anything: the NCO computes `strobe`/`is_midpoint`/`mu_out` the SAME cycle it feeds `mu_in` to the interpolator, but `gmsk_step2a_interpolator` is a **19-stage registered pipeline** (confirmed by direct count of `always @(posedge aclk)` blocks in its source, not estimated) -- the interpolator's own output for that `mu_in` doesn't appear until 19 cycles later. Feeding the TED today's tag alongside whatever the interpolator happens to output THIS cycle would silently pair the wrong tag with the wrong sample.

Built `hdl/gmsk_interp_tag_delay/gmsk_interp_tag_delay.v`: a plain, unconditionally-shifting 19-deep x 2-bit shift register (`DELAY_CYCLES=19` parameter, explicitly tied to and documented against the interpolator's measured latency, with a note on how to re-verify it -- `grep -c "always @(posedge aclk)"` -- if the interpolator's own pipeline ever changes). Safe to run unconditionally (no gating on any valid signal) because the interpolator's own pipeline was independently confirmed to never stall -- every stage updates every clock cycle regardless of gaps in the real ADC valid signal, so the latency is a fixed, deterministic constant.

**SIM gate hit a real testbench bug, caught and fixed before trusting it:** the first version compared `strobe_out` at loop iteration `i` against `strobe_hist[i - DELAY_CYCLES]`, and failed with ~250 mismatches. Rather than assume the RTL was wrong, hand-traced a small concrete `DELAY_CYCLES=2` example by hand (actual register contents, cycle by cycle) before touching either the RTL or the check further -- confirmed the RTL's actual hardware latency IS genuinely 19 cycles as intended, but a testbench that drives input and checks output within the SAME loop iteration/same clock edge inherently observes the relationship as `output(i) = input(i - (DELAY_CYCLES-1))`, not `input(i - DELAY_CYCLES)`, because that shared edge is simultaneously the input's entry point AND the first of the DELAY_CYCLES edges needed for it to reach the output tap. Fixed the comparison offset (not the RTL), re-ran: **TEST PASSED**, bit-exact across 500 pseudo-random cycles including isolated pulses, back-to-back pulses, long gaps, and the pre-fill (post-reset, not-yet-primed) period.

**IP packaged** (`ip_repo/gmsk_interp_tag_delay/component.xml`, well-formed, all 6 ports present).

## Rebuild after the Stage 2b1/2b2 fix: interpolator fix confirmed working, but a different real bug surfaced in gmsk_step2b2_nco (2026-08-24)

Rewired the updated interpolator IP + tag-delay (`DELAY_CYCLES=20`) into the block design and ran a genuinely fresh rebuild (`reset_run synth_1`, not just `impl_1` -- RTL actually changed this time). Also had to explicitly re-set `gmsk_interp_tag_delay_0`'s `DELAY_CYCLES` on the block-design INSTANCE itself: its value was recorded as an explicit `resolve_type:"user"` `19` in the generated `.xci` from when it was first instantiated, and `upgrade_ip` alone does NOT propagate a changed IP-catalog default onto an already-placed instance's recorded parameter -- would have silently stayed stale at 19 otherwise. Set via `set_property CONFIG.DELAY_CYCLES {20} [get_bd_cells gmsk_interp_tag_delay_0]` after `open_bd_design`, confirmed `20` in the regenerated `.xci` before trusting it.

**Good news: zero violations traced to `gmsk_step2a_interpolator` anywhere in this build** -- the Stage 2b1/2b2 split genuinely fixed what it targeted.

**Bad news: a different, real, PRE-EXISTING bug surfaced, unrelated to that fix.** This was the first genuinely fresh full resynthesis `gmsk_step2b2_nco` had ever gotten (every earlier rebuild only did `reset_run impl_1`, reusing that module's original, never-refreshed OOC synthesis output) -- so this bug had been latent since the very first B2 build, just never the WORST path in any report until the interpolator's own (worse) violations got fixed out of the way. Worst path: `gmsk_step2b2_nco_0/phase_acc_reg[1]/C -> mu_out_reg[N]/CE`, -0.340ns, an 8-level CARRY4 chain (the full `sum_ext` accumulate). 10 of the ~20 listed violations were this SAME systemic issue across different `mu_out` bit positions (one root cause, many endpoints) -- the other violations were pre-existing `axi_ad9361` RX-channel infrastructure (untouched by us) and the usual accepted `system_ila_0`-only category.

**Root cause: the original single-stage `gmsk_step2b2_nco` decided `strobe`/`is_midpoint`/`mu_out` combinationally in the SAME cycle as the full `STEP_WIDTH`-bit accumulate** (`wrap_w`/`mid_cross_w` depend on the accumulate's own carry-out/top-bit). Vivado inferred a clock-enable (CE) pin for those output registers, gated by logic that needed the ENTIRE wide add to settle first, all in one 4ns cycle. Exactly the same "don't decide-and-update from a wide combinational result in one cycle" lesson `gmsk_step2a_interpolator`'s six real-hardware bugs already taught this project -- just never applied to this module before, since its own SIM gate (pure arithmetic correctness) can't catch a synthesis-timing issue, and no earlier build had a fresh enough netlist to expose it.

**Fix, same shape as every other instance of this lesson:** split into two registered stages. Stage 1 computes the accumulate and REGISTERS `wrap`/`mid_cross`/`mu` as plain flip-flop outputs (nothing downstream happens combinationally in the same cycle). Stage 2 decides `strobe`/`is_midpoint`/`mu_out` from those already-settled, single-bit stage-1 registers -- still a CE-style conditional update, but now gated by a trivial 2-3-input decision instead of a 32-bit carry chain. Costs one extra cycle of latency (`sample_valid` to `strobe`/`mu_out`/`is_midpoint`: 1 cycle -> 2 cycles).

**Worked out carefully, before writing any RTL, whether this ripples into `gmsk_interp_tag_delay`'s `DELAY_CYCLES` calibration -- it does NOT.** That parameter measures the INTERPOLATOR's own input-port-to-output-port latency alone (a fixed property of that module, unrelated to how many cycles the NCO itself takes to decide). Since `strobe`/`is_midpoint`/`mu_out` still move together in lockstep through the new extra stage (all three update on the exact same Stage-2 cycle, same as before), their mutual alignment -- the only thing `tag_delay`'s calibration actually depends on -- is unchanged. `DELAY_CYCLES` stays 20, no edit needed there.

**SIM gate rewritten, not just re-run, and this one needed a real testbench redesign, not just parameter tweaks:** the ORIGINAL `gmsk_step2b2_nco` testbench used the single-process "check immediately after driving" pattern -- valid only because the original DUT was a single register stage. Reusing it on the new 2-stage DUT would hit the exact same class of bug `gmsk_step2d_gardner_ted`'s own testbench development already ran into once. Switched proactively to the PROVEN self-synchronizing capture pattern instead (a separate process capturing `is_midpoint`/`mu_out` into an array every cycle `strobe` pulses, compared against a pre-filtered `expected_events_ismid.hex`/`expected_events_mu.hex` -- same `expected_ontime.hex`-style convention `gmsk_step2d_gardner_ted`'s own generator already established) -- sidesteps needing to hand-count the new latency at all. **TEST PASSED, bit-exact across all 1500 real events, clean on the first try** (the lesson genuinely transferred this time, no new off-by-one to debug).

**IP repackaged**, all 8 ports confirmed present in the regenerated `component.xml`. **Not yet rewired into the block design or rebuilt** -- deliberately stopped here to report the finding rather than immediately re-triggering another long rebuild, given how many rebuild cycles this specific bitstream has already needed.

## gmsk_step2b2_nco fix rebuilt and rewired: both interpolator + NCO fixes confirmed clean; one pre-existing infra violation category remains (2026-08-23/24)
